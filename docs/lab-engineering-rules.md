# 랩 엔지니어링 규칙 — 2026-10-23 세션 회고에서 도출

> **출처:** 2026-10-23 Phase 5 v1.1/v2 실행 세션의 사후 회고. 이날 하네스·검증기·판정 로직에서 반복된 실수를 규칙으로 굳힌 것이다. 일부 항목은 GitHub 이슈 #1이 외부에서 지적한 것(시드 positive control, 실패 전파)과 뿌리가 같다 — 외부 리뷰 전에 스스로 잡았어야 할 것들이다.
>
> **적용 시점:** 새 하네스/러너/검증기를 쓰거나 고칠 때, 증적 감사를 보고할 때, 결과 문서를 작성할 때 아래 체크리스트(§3)를 통과했는지 확인한다.

## 1. 규칙

### R1. 라이브니스 단언 — "시험 대상에 실제로 닿았는가"를 먼저 증명한다

모든 하네스는 본 실험 요청 전에 워밍업/헬스 요청이 **반드시 성공**했음을 단언하고, 실패 시 계속 진행하지 않는다. 음성 대조군의 "통과"는 시험 대상이 실제로 작동했을 때만 의미가 있다.

- **사례:** `lifecycle-fuzz.py` 초판이 재사용 서버의 실제 포트(18087)와 다른 포트(18086)로 요청을 보내, 8개 시퀀스 전부가 닫힌 포트를 두드렸는데도 음성 대조 2건이 "기대 충족"으로 통과했고, 첫 실행 결과가 그럴듯한 신호처럼 보여 잘못된 방향(생산자 튜닝)으로 진단을 시작했다. `producer_request: None`이라는 결정적 신호를 "튜닝 문제"로 해석한 것이 두 번째 오류였다.
- **적용:** 워밍업 실패 → 즉시 중단 + `error: warmup_unreachable` 기록. "왜 실패했는가"보다 "도달은 했는가"부터.

### R2. 검증기는 증적을 실제로 커버해야 한다 — "passed"의 커버리지를 함께 보고한다

새 러너를 추가하면 그 result 스키마를 `verify-evidence.py` 검사 대상에 **등록**한다(필요시 `verdict.mode` 등 버킷 키 명시). 검사기가 새 증적을 건너뛰거나 형식만 맞아 통과한다면 그렇게 보고한다. 녹색 상태 자체가 목적이 되게 하지 않는다.

- **사례:** `gdb-pathb`/`gdb-patha` 결과에 `mode` 필드가 없어 check_gdb의 기본 `serialize` 버킷에 들어가 **진짜 serialize 증적을 감사에서 대체**했고, 스키마가 맞지 않는 레코드가 우연히 요건을 충족해 통과했다. `poc-patha` 매트릭스(`result-*.json` 네이밍)와 `probe-pathc-*` 반복 증적은 애초에 poc 검사 glob 밖이었다. 즉 "verify-evidence passed"는 참이었지만 새 증적 상당수가 감사 범위 밖이거나 형식적 통과였다. 이 위험을 인지하고도 "어차피 통과하니 그대로 두자"고 넘어갔다.
- **적용:** 새 증적 유형 추가 시 ① 검사기 등록 여부 ② "실제로 검사된 레코드 수" 단언(0건이면 실패 — R7 참조) ③ 요약에 커버리지 명시.

### R3. 생성한 코드는 즉시 구문 점검한다 — 이스케이프가 필요한 코드는 Write 도구로만 쓴다

wsl/heredoc/인라인 생성 파일은 작성 직후 `python3 -m py_compile`(또는 `bash -n`)을 돌린다. `\n`, `\xNN` 등 이스케이프를 포함한 코드를 셸 경유로 생성하지 않는다 — 리터럴 기록(Write 도구)으로만.

- **사례:** heredoc 생성 시 `\\n`이 실제 줄바꿈으로 붕괴해 `verify-evidence.py` 2회(픽스처 블록, BOM 바이트 리터럴), `lifecycle-fuzz.py` 1회 SyntaxError, `apache-patha-matrix.sh` 줄결합 붕괴. 첫 실패로 원인을 알았음에도 같은 경로를 3번 이상 반복했다.
- **적용:** 셸로 코드를 "생성"하는 순간 그 직후 컴파일 검사가 의무. 붕괴가 확인되면 그 세션에서는 해당 경로를 다시 쓰지 않는다.

### R4. 재사용하는 코드의 계약을 읽고 연결한다

재사용 대상(서버 클래스, 러너, 설정)의 **입력 계약** — 포트는 모듈 상수인가, 설정은 생성자 인자인가 `os.environ`인가 — 를 코드에서 확인한 뒤 연결한다. "비슷하니까 되겠지"로 붙이지 않는다.

- **사례:** ① `poc-bgserialize.Server`는 포트를 모듈 상수(18087)로 하드코딩 — 내 상수(18086)와 불일치(R1의 사례). ② 같은 클래스가 `POC_MEMORY_LIMIT`을 **전달된 env가 아니라 `os.environ`**에서 읽어, 시퀀스별 한도 설정이 무시되고 전부 기본 8M으로 실행됐다. ③ `post_max_size=4M`(config/php.ini)이 14MB 생산자 본문을 선거부했는데, 로그를 읽기 전에 "OOM 튜닝 문제"로 오진했다 — 실제 원인은 로그 첫 줄에 있었다.
- **적용:** 재사용 즉시 "이 클래스의 설정은 어디서 오는가" 한 번 grep. 진단 시 로그 원문을 가설보다 먼저 연다.

### R5. 판정 마커는 실제 로그/메시지 출력에서 채택한다

문자열 포함 여부로 판정하는 로직(`'X' in log`)을 쓸 때, 그 문자열이 **실제 출력에 존재하는지** 먼저 확인한다. 함수명이 에러 메시지에 안 나오는 것처럼 "있을 법한 마커"는 자주 없다.

- **사례:** `poc-pathc`의 생산자 판정을 `'unserialize' in 로그`로 썼지만 fatal 메시지엔 함수명이 없다(실제 마커는 엔드포인트 file:line). ground-truth 실행에서 P17 기대 미충족으로야 드러났다.
- **적용:** 판정식 작성 전 대표 로그 1건을 붙여넣고 마커가 실제 존재하는지 눈으로 확인.

### R6. 기대 모델은 추상화가 아니라 메커니즘에서 유도한다

"잔류 상태 + 소비자 요청 = 메모리 오류" 같은 일반화로 기대값을 만들지 않는다. 어떤 상태가 어디서·어떤 전제로 소비되는지(findings의 확립된 경로 정의)에서 다시 유도한다. **위음성이 보이면 "하네스가 틀렸는가"보다 "내 기대가 틀렸는가"를 먼저 검토**한다.

- **사례:** `lifecycle-fuzz` 초안이 생산자+중간 요청 없음 → 무조건 오류로 예측했으나, no-file 소비자는 stale `PS(id)`만 소비하고 런타임 생산자 후엔 `PS(id)`가 NULL이라 새 빈 세션을 만들어 decode 자체가 생략된다. 시스템이 아니라 모델이 틀렸다. 탐색 맥락에서 이 방향의 오류는 잘못된 기대에 하네스를 맞춰 실제 동작을 덮는 사고로 이어질 수 있다.
- **적용:** 기대식 옆에 근거(경로/전제)를 주석로 남긴다. 근거 없는 기대식은 경고 대상.

### R7. 배치 실행 전 단일 스텝 + 파라미터 배선 확인

스윕/매트릭스는 반복 전에 1회 실행으로 ① 파라미터가 실제로 전달되는지 ② 상태·판정이 기록되는지 확인한다. `|| true`로 실패를 삼키지 않는다(이미 프로젝트 표준 — 이사 #1 반영). 언어 경계(bash→python argv)에서 타입 비교(`"0" != 0`)를 조심한다.

- **사례:** ① `PARTS` env를 받게 쓰고 실제로는 `--parts 400` 하드코딩인 채로 12회 스윕 낭비. ② `apache-patha-matrix`의 `rc != 0` 문자열 비교 오류로 전 이터레이션이 `runner_failed` — 재실행에서야 적발.
- **적용:** 스윕 스크립트 첫 이터레이션은 `--dry-run`(설정 echo) 또는 로그로 배선 확인 후 나머지 실행.

### R8. 실험 구동부는 `linux/` 아래에 커밋한다 — 결과만 인용하지 않는다

findings에 결과를 인용하는 실험의 러너는 저장소에 있어야 한다. `.zwork/`는 일회성 탐색 전용이며 증적 인용의 근거가 될 수 없다.

- **사례:** B2-a(uploaded_files 스윕)와 P15 조준 루프가 `.zwork`에 남은 채 findings §9에 인용됨 — 증적 파일은 있지만 정확한 재현 스크립트가 저장소에 없다.
- **적용:** findings에 넣는 순간 해당 스크립트를 `linux/`로 옮기고 커밋 목록에 포함.

### R9. wsl.exe 인라인 복잡 명령 금지 — 스크립트 파일 경유로 표준화

`$(...)`, 셸 변수, 중첩 따옴표가 들어간 명령을 wsl.exe 인라인으로 실행하지 않는다. 스크립트 파일을 쓰고 `wsl bash <파일>`로 실행한다. 이는 이미 세션에서 여러 차례 입증된 환경 제약이다.

### R10. 커밋/푸시는 요청 단위로 판단한다

이전 턴의 관례(매 턴 커밋+푸시)를 상시 위임으로 간주하지 않는다. 특히 다른 작업자(다른 LLM 포함)가 같은 저장소에서 작업 중일 때는 push 충돌·섞임 위험이 있으므로 명시적 요청이 있을 때만 한다.

### R11. 문서 커밋 전 오탈자 게이트

한글 문서에 중국어 간체·일본식 한자 혼입(`强제`), 자모 오타(`찞음`)가 실제로 발생했다. 커밋 전 `grep -nP '[\x{4E00}-\x{9FFF}]' docs/*.md` 계열로 한자 혼입을 점검한다(의도한 한자어 제외).

### R12. 증적은 커밋된 드라이버로만 생성한다 — 출처를 증적에 박는다

증적을 만드는 모든 실행(배치·스윕·재생·재도출·진단 포함)은 저장소 `linux/` 아래에 커밋된 스크립트로 구동한다. 스크래치패드·`/tmp`·세션 임시 디렉터리의 스크립트로 인용 가능한 증적을 만들지 않는다.

- **장기 실행 전 드라이버 커밋:** 배치를 시작하기 전에 드라이버를 먼저 커밋한다.
- **출처 기록:** 각 증적 summary에 `source_commit`(실행 시점 HEAD), `source_dirty`(`linux/`에 미커밋 변경이 있는지), `argv`(실행 명령줄)를 기록한다. `source_dirty=true`이면 인용 가능한 증적으로 쓰지 않는다. 실행 중에는 그 실행이 로드하는 코드를 수정하지 않는다.
- **얇은 실행기 허용:** WSL 진입 래퍼처럼 커밋된 스크립트를 고정 인자로 부르기만 하는 실행기는 허용한다. 실제 명령줄은 `argv`로 남긴다.
- **입력 보존:** 재생·재도출의 입력 파일(`/tmp` 등)은 증적 디렉터리로 복사해 보존한다.
- **두 등급:** findings에 인용할 진단은 `linux/diag/`에 커밋해 실행한다. 인용하지 않는 탐색용 스모크는 증적에 `non-citable`로 명시한 경우에만 커밋 없이 허용한다.
- **기존 증적:**
  - 2026-10-23 이전·도중에 커밋된 드라이버로 실행한 배치(g34·G5·rederive)는 "argv·source_commit 미기록"이라는 한계를 증적에 명시한다.
  - 스크래치패드 인라인 코드로 생성해 findings에 **인용한** 증적(Path B 자기 교착 fd·잠금 분석, 관측자 효과 대조)은 `linux/diag/`의 커밋된 스크립트로 재실행해 결과 일치를 확인한다. 불가능하면 그 한계를 증적과 findings에 명시한다.
- **사례:** 2026-10-23 세션에서 진단 다수를 스크래치패드 인라인 Python으로 실행했고, 그중 자기 교착 분석이 findings §10.7에 인용됐다. replay 입력은 `/tmp`에만 있었고, G5 배치 도중 탐색기 파일을 수정했다(동작 보존 변경이었지만 증적만으로는 확인할 수 없음).

## 2. 반복 원인의 요약 (규칙이 막는 것)

| 근본 패턴 | 막는 규칙 |
|---|---|
| 안전망 부재(구문 점검·단일 스텝·라이브니스 단언 없음) | R1, R3, R7 |
| 재사용 계약·로그 형식을 관측 전에 가정 | R4, R5 |
| 녹색 신호(통과)의 커버리지를 의심하지 않음 | R2, R6 |
| 학습한 환경 결함에 표준 우회책 적용 지연 | R3, R9 |
| 증적 기준의 자기 예외화 | R8, R10, R11, R12 |

## 3. 체크리스트

**새 하네스/러너 작성 시:** R1 워밍업 단언 · R3 구문 점검 · R4 재사용 계약 확인 · R6 기대식 근거 주석 · R7 단일 스텝 선행.

**증적 감사 보고 시:** R2 검사기 등록 + 검사 레코드 수 단언 + 커버리지 명시 · R8 러너 커밋 여부 · R12 source_commit·argv·입력 보존·dirty 여부.

**문서화/커밋 시:** R5 마커 실재 확인(판정식 변경 시) · R11 오탈자 게이트 · R10 요청 단위 판단.
